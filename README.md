# Визуализатор графа зависимостей Maven (вариант 8)

Практическая работа №2 по дисциплине «Конфигурационное управление».
Готовы этапы 1–4 из 5: конфигурация, сбор данных, основные и дополнительные операции.

## Общее описание

Консольное приложение для анализа зависимостей пакетов Java (Maven).
Менеджеры пакетов и сторонние библиотеки для получения зависимостей
не используются: описание пакета (`pom.xml`) скачивается по URL
репозитория и разбирается стандартными модулями Python.

На этапе 3 приложение строит граф зависимостей с учётом транзитивности
и выводит его списком рёбер. Вывод параметров был только на этапе 1,
вывод одних прямых зависимостей — только на этапе 2.
С опцией `-l` выводится порядок загрузки зависимостей (этап 4).

## Функции и настройки

| Опция | Параметр | По умолчанию |
|---|---|---|
| `-p`, `--package` | анализируемый пакет `groupId:artifactId:version`; в режиме `test` — большие латинские буквы | обязательна |
| `-s`, `--source` | URL репозитория или путь к файлу тестового репозитория | `https://repo1.maven.org/maven2` |
| `-m`, `--mode` | режим работы: `remote` — настоящий репозиторий, `test` — тестовый | `remote` |
| `-o`, `--image` | имя PNG-файла с изображением графа | `graph.png` |
| `-d`, `--depth` | максимальная глубина анализа, целое от 1 | `5` |
| `-e`, `--exclude` | не учитывать пакеты, имя которых содержит подстроку | пусто |
| `-l`, `--load-order` | вывести порядок загрузки зависимостей вместо графа | выключена |

Ошибки, которые проверяются:

- пакет не в формате `groupId:artifactId:version` (в режиме `test` — не из букв `A-Z`);
- неизвестный режим;
- источник не `http(s)`-адрес, а в режиме `test` — файл не существует;
- изображение не `.png` или папка для него не существует;
- глубина не целое число или меньше 1;
- подстрока фильтра содержит пробелы.

При ошибке приложение пишет `config error: ...` и завершается с кодом 1.
Если опция `-p` не задана совсем, справку и ошибку печатает `argparse`,
код завершения 2.

### Как находятся прямые зависимости

1. По координатам строится адрес файла:
   `{репозиторий}/{groupId с / вместо .}/{artifactId}/{version}/{artifactId}-{version}.pom`.
2. Из `pom.xml` берётся раздел `<dependencies>` верхнего уровня.
   Плагины сборки (`<build>`) и профили не учитываются.
3. Версии вида `${hamcrestVersion}` подставляются из `<properties>`.
4. Если версия не указана, она берётся из `<dependencyManagement>`
   самого пакета, его родительских `pom.xml` (`<parent>`) и файлов BOM,
   подключённых через `<scope>import</scope>`.
5. Для каждой зависимости выводится область (`compile`, `test`, `runtime`,
   `provided`) и признак `optional`.

Ошибки: пакета нет в репозитории, нет связи, повреждённый `pom.xml`.

### Построение графа

Алгоритм — обход в глубину (DFS) **без рекурсии**, по явному стеку
(`src/graph.py`, функция `build_graph`).

- Для графа берутся зависимости, которые Maven переносит транзитивно:
  область `compile` или `runtime`, без `optional`. Зависимости `test`
  и `provided` в граф не попадают.
- Глубина анализируемого пакета — 0. Пакеты на глубине `--depth`
  попадают в граф, но не раскрываются (в выводе: `not expanded`).
  Если до пакета позже найден более короткий путь, он раскрывается заново.
- Пакеты, имя которых содержит подстроку `--exclude`, отбрасываются
  вместе со всем, что доступно только через них.
- Циклы ищутся отдельным обходом без рекурсии (`find_cycles`): ребро в пакет,
  который уже есть в текущем пути. Обход при цикле не зацикливается,
  каждый цикл выводится строкой `Cycle:`.
- Если `pom.xml` зависимости получить не удалось, она остаётся листом,
  причина выводится строкой `Not loaded:`.

### Порядок загрузки (`-l`)

Пакет можно загрузить только после всех его зависимостей. Порядок
строится обратным обходом в глубину без рекурсии (`load_order` в
`src/graph.py`): пакет попадает в список, когда пройдены все его
зависимости. Анализируемый пакет всегда последний. Для пакетов цикла
такого порядка не существует: они помечены `(cycle)`, ребро, замыкающее
цикл, при построении порядка пропускается.

### Сравнение с Maven

Скрипт `examples/compare_with_maven.sh ПАКЕТ` создаёт временный проект
с одной зависимостью и выводит рядом результат этого инструмента,
`mvn dependency:tree` и `mvn dependency:build-classpath` (порядок, в котором
Maven отдаёт библиотеки Java). Нужен установленный Maven
(`brew install maven`).

### Результаты сравнения (Maven 3.10.0)

| Пакет | Этот инструмент | Maven |
|---|---|---|
| `spring-context:6.0.13` | 5 зависимостей | те же 5 |
| `guava:32.1.3-jre` | 6 зависимостей | те же 6 |
| `logback-classic:1.4.11` | 2 зависимости | те же 2 |
| `okhttp:4.12.0` | 11 зависимостей | 7 |

**Порядок различается всегда.** Maven (`dependency:build-classpath`) ставит
пакет раньше его зависимостей, в порядке объявления, по уровням дерева:

```
okhttp, okio, okio-jvm, kotlin-stdlib-common:1.9.10, kotlin-stdlib-jdk8:1.8.21, ...
```

Этот инструмент строит порядок, при котором каждая зависимость загружена
раньше пакета, которому она нужна: `kotlin-stdlib-common`, ..., `okhttp`
последним. Это два разных смысла «порядка»: Maven перечисляет
библиотеки для поиска классов (classpath), здесь — порядок установки.

**Набор пакетов у `okhttp` различается.** `okhttp` зависит от
`kotlin-stdlib-jdk8:1.8.21`, а через `okio-jvm` — от `kotlin-stdlib:1.9.10`.
Maven оставляет одну версию каждой библиотеки по правилу «ближайшая
побеждает»: `kotlin-stdlib` версии 1.8.21 находится ближе к `okhttp`
(глубина 2), чем 1.9.10 (глубина 3), поэтому 1.9.10 и всё, что тянется
только через неё, Maven отбрасывает. Здесь версии не сводятся: в граф
попадают и 1.8.21, и 1.9.10 — отсюда 11 пакетов против 7.

Другие возможные причины расхождений:

| Расхождение | Причина |
|---|---|
| у Maven меньше пакетов | Maven учитывает `<exclusions>` в `pom.xml`, здесь они не читаются |
| другие версии | Maven применяет `dependencyManagement` анализируемого проекта ко всему дереву, здесь — к каждому `pom.xml` отдельно |
| нет пакетов из профилей | профили `<profiles>` здесь не учитываются |
| граф короче | действуют `--depth` и `--exclude` |
| циклы | Maven отказывается собирать проект с циклом, здесь цикл выводится и помечается |

### Тестовый репозиторий (`-m test`)

Вместо URL указывается путь к текстовому файлу. Пакеты называются
большими латинскими буквами:

```
# комментарий
A -> B, C
B -> D
C -> D
D ->
```

Примеры в `examples/repos/`:

| Файл | Случай |
|---|---|
| `simple.txt` | две прямые зависимости |
| `diamond.txt` | общая зависимость (ромб) |
| `chain.txt` | длинная цепочка, проверка `--depth` |
| `exclude.txt` | проверка `--exclude TEST` |
| `cycle.txt` | цикл `A -> B -> C -> A` |
| `self.txt` | пакет зависит сам от себя |
| `undefined.txt` | зависимость не описана в файле — лист |
| `broken.txt` | ошибка формата |

### Файлы

| Файл | Назначение |
|---|---|
| `src/app.py` | точка входа, вывод |
| `src/config.py` | опции командной строки и их проверка |
| `src/maven.py` | скачивание и разбор `pom.xml` |
| `src/graph.py` | обход в глубину без рекурсии, поиск циклов |
| `src/local_repo.py` | чтение тестового репозитория |
| `examples/stage1_demo.sh` | все опции и ошибки в них |
| `examples/stage2_demo.sh` | прямые зависимости настоящих пакетов |
| `examples/stage3_demo.sh` | граф на всех тестовых репозиториях и на Maven Central |
| `examples/stage4_demo.sh` | порядок загрузки |
| `examples/compare_with_maven.sh` | сравнение с настоящим Maven |

## Сборка и тесты

Сборка не нужна, требуется Python 3.9+. Сторонние пакеты не нужны.

```bash
make test                 # модульные тесты
make demo                 # примеры этапов 1–4
./run.sh -p junit:junit:4.13.2
```

Без `make`:

```bash
python3 -m unittest discover -s tests -v
python3 -m src.app -p junit:junit:4.13.2
```
